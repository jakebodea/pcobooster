# API architecture

The product API is a contract-first oRPC service served by Hono inside an Alchemy Effect-native Cloudflare Worker (`apps/server/src/worker.ts`). Effect owns application execution below the transport boundary. Better Auth remains an ordinary HTTP handler because it defines its own protocol and routes.

## Package boundaries

- `packages/contracts` contains browser-safe oRPC contracts, transport DTO schemas, and safe error payload schemas. It must not import database, auth, Hono, framework, or Effect modules.
- `packages/planning-center-models` contains shared Planning Center data shapes plus pure calendar and scheduling rules. It is browser-safe and framework-independent.
- `packages/presentation-mode` contains the server-side presentation-mode guard, seed, and cache namespace shared by the API and the web build, which inlines the namespace.
- `packages/api` contains server-side application programs, typed faults, explicit feature modules, Better Auth and database integration, Planning Center adapters, and the oRPC implementation of the contracts.
- `apps/server` is the API Worker. It reads its settings with `Config` at startup, binds D1 and the Planning Center cache KV namespace, builds the server dependencies once per isolate, mounts Better Auth and the oRPC handlers, supplies raw request context, and configures cross-origin and response-header behavior.
- `apps/web` consumes `packages/contracts` through the oRPC client and owns browser caches, hydration, navigation, and presentation helpers under `src/lib`. It must not import server-side modules from `packages/api`.

## Request flow

```text
apps/web
  -> oRPC contract client
  -> apps/server /api/rpc
  -> packages/api transport adapter
  -> Effect application program
  -> packages/api feature module
  -> Planning Center or database adapter
```

The Worker builds `ServerDependencies` (`packages/api/src/server.ts`: the typed `ServerConfig`, the Drizzle database, Better Auth, the feature flag client, the Planning Center read caches, and the feature-module read caches) once per isolate. The Worker's construction phase acquires the D1, KV, and Cloudflare Flagship bindings, as `Cloudflare.D1.QueryDatabase`, `Cloudflare.KV.ReadWriteNamespace`, and `Cloudflare.Flagship.ReadFlags`, and passes the raw bindings in. Programs evaluate flags per request with `featureFlags.isEnabled(name, subject)`, never from configuration; see [Feature flags](environment.md#feature-flags). The oRPC context carries them, and every execution provides them to the program as the `Server` service; `packages/api` never reads `process.env` or `cloudflare:workers`. One process-scoped `ApplicationRuntime` owns shared Effect layers. Every execution also provides a new `RequestContext`, including a request ID, cloned headers, method, URL, user-agent metadata, and abort signal. Credentials and other identity-sensitive values belong in request-scoped services; they must not be captured by a process-scoped layer or implicit async context. Planning Center clients bind one explicit credential to both their Authorization header and cache scope for their entire lifetime. A [demo session](demo.md) resolves to the demo credential through a read-only client that rejects writes before they leave the process, and always presents people with fictional details.

Application programs fail with tagged application faults rather than HTTP statuses. The oRPC adapter maps each expected fault to a declared contract error once. Planning Center HTTP, network, and malformed-response errors are classified at the provider boundary; unexpected adapter errors remain Effect defects. Defects and persistence failures are returned as opaque internal errors, with their original cause retained only for server-side logging.

All oRPC and OpenAPI responses are marked `Cache-Control: private, no-store` at the Hono boundary. oRPC's response-header plugin preserves procedure-specific headers such as account-selection cookies.

## Planning Center adapters

The Planning Center client (`packages/api/src/planning-center/core-client.ts`), the services under `planning-center/services/`, and the feature modules under `modules/planning-center/` return Effects end to end. Their typed failure channel is `PlanningCenterError`: `PlanningCenterApiError` (an error status or unusable response), `PlanningCenterNetworkError` (fetch, body stream, or attempt timeout), `PlanningCenterReadOnlyError` (a blocked demo write), `PlanningCenterRateLimitError` (the credential's rate budget is spent for longer than the wait cap, so the request was not sent), and `PlanningCenterSubrequestLimitError` (Cloudflare refused the fetch with "Too many subrequests", or the procedure's request budget is spent). Application programs compose them directly and translate that channel once with `withPlanningCenterFaults`, which maps read-only writes to `Forbidden`, 429 responses and pacing rejections to `RateLimited` (with `retryAfterSeconds`), and subrequest limits and other provider failures to `ExternalServiceFailure`; anything else stays a defect.

- **Failure recovery.** A Planning Center failure never becomes empty or default data by accident. Code under `planning-center/` and `modules/` recovers only through `recoverPlanningCenterFailure` (`planning-center/recover-failure.ts`), naming the kinds it may fall back after: `not-found` (a 404), `provider-failure` (any other error status except 429, or a network failure), or `unusable-response` (a defect). Rate limits (`PlanningCenterRateLimitError` or a 429), subrequest limits (`PlanningCenterSubrequestLimitError`), read-only rejections, and interruption always propagate, whatever the caller lists. Each fallback logs its reason with the ids involved: `not-found` at `info`, anything else at `warn`. Code that needs a different recovery than a fallback value (the team positions series lookup) gates it with `isRecoverablePlanningCenterCause`. `lint/architecture-boundaries.test.ts` fails when an Effect recovery combinator appears in that code outside a short, justified list, and `testing/planning-center-failures.ts` lists the budget failures each recovery site is tested against. The remaining fallbacks:
  - Organization time zone: the configured `PLANNING_CENTER_TIME_ZONE` after a provider failure or unusable response, cached for 2 minutes.
  - A service type another organization owns (People dashboard activity, person detail): its schedules keep their plan dates, without rehearsal times.
  - A plan Planning Center does not find: no plan times.
  - A song never scheduled for the service type: no last scheduled item.
  - Deleting a plan time that is already gone: the delete succeeds.
  - Team positions: a failed service-type needed positions read tries the plan's series once.

  Everything else fails the procedure as a typed fault; progressive procedures return partial data only through their continuations (see [Progressive procedures](#progressive-procedures)), and the browser offers Retry.

- **HTTP.** The client sends through an `effect/unstable/http` `HttpClient`. The process-scoped `ApplicationRuntime` provides `FetchHttpClient.layer`, `resolvePlanningCenterAccess` reads that client from context, and the request's services bind it together with the request credential for their lifetime. Tests pass an `HttpClient` over a scripted `fetch` (`testing/http-client.ts`).
- **Retries and timeouts.** Only idempotent reads (GET and HEAD) retry, on a `Schedule` of at most two retries: 408, 429, 500, and 502 to 504 responses and attempt timeouts qualify; 429 waits for `Retry-After`, other responses back off 500 ms per retry, and timeouts 300 ms. A 429 whose `Retry-After` is longer than 5 seconds is not retried: the read fails at once with the 429 (`RateLimited` with `retryAfterSeconds`) so the browser can retry instead of holding the request open. A subrequest limit is never retried. Each attempt (pacing wait, request, and error body) has a 15 second Effect timeout, and the JSON body read uses what remains of that budget.
- **Pacing.** `PlanningCenterRatePacer` (`planning-center/rate-pacer.ts`) keeps one window per credential (cache scope) in the isolate, learned from each response's `X-PCO-API-Request-Rate-Limit`, `-Count`, and `-Period` headers; it never assumes 100 per 20 seconds. The process-scoped `ApplicationRuntime` provides one pacer as the `PlanningCenterPacing` service, so every procedure for the same credential in the isolate shares it. Until half the reported limit is used (counting requests still in flight), reads go straight out. After that, each read takes the next slot, spaced `time left in the window / requests left`, so the remaining budget is spread across the window before sending rather than paused after the response. A 429 blocks the credential until its `Retry-After`. A read whose slot is more than 5 seconds away fails with `PlanningCenterRateLimitError` (`reason: "budget"`) without being sent. Reads from a speculative procedure (see [Request priority](#request-priority)) never wait: they go out only while the window is below 40% of the reported limit, nothing is blocked by a 429, and no interactive read is waiting for a slot, and otherwise fail at once with `PlanningCenterRateLimitError` (`reason: "speculative"`), so the rest of every window stays for what the user is waiting on. Writes are counted but never delayed or rejected by the pacer, keep their no-retry rule, and still follow the provider-write boundary below. The pacer cannot see other isolates, tabs, or devices using the same Planning Center user; only a Durable Object per user could.
- **Request accounting.** A root oRPC middleware (`transport/orpc/implementation.ts`, `transport/orpc/planning-center-accounting.ts`) creates one `PlanningCenterRequestAccounting` per procedure call and puts it in the oRPC context; `executeApplicationEffect` provides it to every execution in that procedure as the `PlanningCenterAccounting` service. The client counts each request it sends (retries included), paced requests and their wait, 429s, pacing rejections, and subrequest-limit hits. Programs read the count with `planningCenterRequestsSpent` (`planning-center/request-budget.ts`) to stop early and return partial data. Every procedure has a hard cap, `PLANNING_CENTER_REQUEST_CAP` (40): past it the client fails with `PlanningCenterSubrequestLimitError` (`source: "budget"`) before Cloudflare would refuse the fetch. The count covers Planning Center API requests only, so the cap leaves 10 of Workers Free's 50 subrequests for the rest, counted from the code in `NON_PLANNING_CENTER_SUBREQUEST_RESERVE`: the account and token reads (3 D1 queries, since `getAccessToken` bypasses the session cookie cache), an access token refresh (2), an expired session cookie cache (2), one shared-tier KV read and write (2), and a feature flag (1). The rare `refreshToken` fallback adds 4 more; if it coincides with a full procedure, Cloudflare refuses the fetch and the procedure fails with a typed fault. After Cloudflare refuses one fetch, later requests in the same procedure fail at once without being sent. Code outside a procedure (scripts, most unit tests) has no accounting and no pacer; budgeted modules give themselves a fresh count there (`withPlanningCenterRequestCount`), so their counts are always real.
- **Logs.** Every pacing wait, pacing rejection, and 429 is logged at `info` with the endpoint (path and query parameter names only, never values, tokens, or bodies), method, attempt, wait or `Retry-After`, and the rate-limit headers. Cloudflare "Too many subrequests" refusals log at `warn`. Each procedure that touched Planning Center logs one `info` line, "Planning Center procedure summary", with the procedure path (for example `people.planWindowHistory`), request ID, duration, outcome, and its counts. The client and the summary take an injectable `PlanningCenterLogger`; they default to the pino module loggers.
- **Caches.** `cachedRead` (`planning-center/services/cached-read.ts`) adapts an Effect load to the shared `PlanningCenterReadCache`. The load is built only on a miss and runs in its own fiber, so each caller waits independently. A load runs with the priority of the procedure that started it; an interactive caller that joined a speculative load the pacer held back loads again with its own priority rather than failing with the prefetch.

Cancellation is Effect interruption. A read runs in the request's fiber, which the transport interrupts when the Fetch request aborts; interrupting a Planning Center call aborts its in-flight fetch, pacing wait (releasing its slot), or pagination. Shared cache loads keep per-caller waiters: one disconnected caller does not cancel another, but the load is interrupted and its result is not cached when no callers remain. Reads that fall back after a failure (such as the organization time zone) still stop when interrupted. At the provider-write boundary, the application checks the request signal once more (`ensureRequestIsOpen`); writes run without request-driven interruption, so after a write starts, execution waits for the provider result and required invalidation or audit work instead of reporting a cancellation while a hidden write continues.

## Request priority

Every call from one person spends the same Planning Center budget, so the browser and the API both put what the user is waiting on ahead of work that only might be needed. `@pcobooster/contracts/request-priority` defines the two priorities:

- **Interactive:** data on screen, or what a click just asked for. The default.
- **Speculative:** loaded ahead of a likely next step: hover and focus prefetches, the Plan tab's items and the plan-window history while the positions list is on screen, and the Plan tab's song options.

In the browser (`apps/web/src/lib/request-priority.ts`), the oRPC link counts interactive calls in flight and sets the `x-pcobooster-priority: speculative` header on speculative ones. Speculative tasks go through `requestScheduler.runSpeculative`: they run one at a time, in order, and each starts only once no interactive call has been in flight for 250 ms (long enough for the query the next render starts from a response, such as candidate details after candidates). A task whose page is left before its turn is dropped. `useIntentPrefetch` schedules every hover prefetch this way, and a newer intent replaces one still waiting. Prefetched queries are marked with `speculativeQuery`; their query functions call oRPC through `callForQuery`, which sends speculative only while nothing on screen observes the query, and resends a held-back call as interactive when the user opened what was being prefetched.

On the API, the root oRPC middleware reads the header into the procedure's `PlanningCenterRequestAccounting` (`priority`), the procedure summary logs it, and the pacer applies it (see Pacing above). A held-back speculative call maps to `RateLimited` like any pacing rejection; prefetches ignore it.

## Progressive procedures

Screens whose data would take more than one invocation's subrequests are split into small procedures the browser calls progressively. Each call plans against `PROGRESSIVE_REQUEST_BUDGET` (36: the cap less room for retries of reads it already admitted), admitting work by upper-bound costs and then counting what was really sent, so cached reads leave room for more work. A procedure that cannot finish returns what it has and a continuation (`deferredPersonIds`, `deferredPlans`, `blockoutProgress`); the browser calls again with it. Every call makes progress, so the browser's "made no progress" guard never trips on large data: each finishes or advances its first unit, using the retry headroom if it must. Failed reads fail the call as typed faults and the browser offers Retry; nothing is swallowed into empty data.

- **People dashboard.** `people.dashboardRoster` (one `teams?include=people` read), then `people.dashboardActivity` for 16 people per call: one schedule page each (two at most), then one plan-range read per service type with rehearsal times, first the service types of the call's first person. That person always finishes; past the cap (more than about ten service types), their remaining schedules keep their plan dates without rehearsal times.
- **Person detail.** `people.dashboardPerson` is one call within the same budget: plan ranges go to the service types missing the most rehearsal times while leaving room for plan-by-plan reads. Times that do not fit keep their plan date, `requestBudget.unresolvedRehearsalTimes` counts them, and the detail view says so under the calendar.
- **Assign view candidate list.** Three procedures (`modules/planning-center/get-position-candidates.ts`, `get-plan-window-history.ts`, `get-candidate-details.ts`) whose results the browser assembles with `assemblePositionCandidates` from `@pcobooster/planning-center-models/position-candidates`, the same code for every client and test:
  - `people.positionCandidates`: the position's assignments and the selected plan's roster, read through its own 30-second cache (`getPlanTeamMembers`) so slot statuses are fresh. About 3 requests cold.
  - `people.planWindowHistory`: the roster of every plan within 28 days of the plan date, across active service types, read in window order until the budget runs out, continued with `deferredPlans` and `deferredServiceTypeIds`. Deferred plans carry their roster pages, so a follow-up call reserves the first one's roster before locating plans again and always reads it. It returns compact roster rows plus the plans and plan times they point at; the browser expands them into history items. It depends only on the date, so every position and plan on that date shares one browser query. Window rosters (`getPlanWindowRoster`) have their own cache, 5 minutes per plan (30 for plans that already happened), so they never stand in for the fresh selected-plan roster; schedule writes clear the plan's copies, and plan time writes clear the account's window rosters.
  - `people.candidateDetails`: whether a blockout covers the plan date, for up to 16 candidates, continued with `deferredPersonIds`. Each person costs one blockout page plus one `blockout_dates` read per repeating blockout that may reach the plan date. A person whose blockout dates do not fit in one call is checked across calls: `blockoutProgress` carries the blockouts already read and whether one covered the day. When the window has no plans at all, the browser asks it for each person's own schedules too (`scheduleHistory: true`), read with `filter=after` from the window start, because Planning Center's default schedule scope is upcoming only. Their rehearsal times are read plan by plan (cached and shared by everyone on the plan), only for plans in the window, at most 12 per person.

  Scores are normalized across available candidates, so they exist only once every part has arrived; until then the list keeps a stable order and shows score placeholders. `position-candidates-equivalence.test.ts` pins the assembled result to the output of the single-call `people.list` it replaced.

## Planning Center read caches

Planning Center reads are cached in two tiers, both keyed by the client's cache scope: `<auth kind>:<sha256 of the credential>`, never the credential itself.

- **Memory** (`PlanningCenterReadCache`): one set per isolate (`PlanningCenterReadCaches`), created with `ServerDependencies` and passed to the services factory; the plan window rosters live there too. It coalesces concurrent loads with per-caller waiters, and mutations invalidate it through `deleteWhere`. Other isolates keep their own copies until the TTL. Caches of values that feature modules derive from those reads live in a second per-isolate set, `ModuleReadCaches` (`modules/read-caches.ts`), created with `ServerDependencies` next to the service caches so the services never depend on module types. Application programs read it from the `Server` service and pass each module its cache as a dependency: the People dashboard person page (2 minutes), the demo organization (10 minutes), the presentation-mode organization id (5 minutes), and ranked song search results (5 minutes). The organization time zone cache (1 hour, or 2 minutes for the configured fallback) belongs to the service caches, and the services factory exposes the resolved zone as `services.organizationTimeZone`. Tests pass fresh caches (`createPlanningCenterReadCaches(null)`, `createModuleReadCaches()`, or `testServer()`), so no test shares cache state with another.

  No cache lives at module scope. `lint/architecture-boundaries.test.ts` fails when code under `packages/api/src/modules` or `packages/api/src/planning-center` creates a `Map`, `WeakMap`, or `PlanningCenterReadCache`, or a `let` binding, at module scope, outside a short, justified exception list (empty today); factories that build caches when called are fine. Two isolate-wide pieces of state remain outside those roots on purpose: the `PlanningCenterRatePacer` the process-scoped `ApplicationRuntime` provides (see Pacing above), and the local-only dev bypass identity (`auth/dev-bypass.ts`), which caches the one identity behind `ServerConfig.localPlanningCenterToken` and never runs outside the local stage.

- **Shared** (`shared-read-store.ts`): a Workers KV namespace per stage (`apps/server/src/planning-center-cache.ts`), bound in `worker.ts` and passed in as a `SharedReadStore`. On a memory miss, a shared cache reads KV before Planning Center and stores what it loads. Store keys are `pc1:<scope>:<cache>:<sha256 of the cache key>`, and a cache key outside its scope is rejected. Values go through a per-cache codec that validates them on the way back, so a malformed entry is a miss.

A cache uses the shared tier only when both hold (`bindReadCaches` in `factory.ts`):

- **No mutation in this app invalidates it.** KV cannot be invalidated reliably across isolates and locations: it is eventually consistent, allows one write per second per key, and on Workers Free allows 1,000 writes a day. A shared cache refuses `deleteWhere`, and a test calls every mutation invalidation with the shared tier on. Its data changes only in Planning Center itself, so the shared tier serves it no staler than the memory tier would: each entry keeps the original load's expiry.
- **A KV hit saves more Planning Center requests than it costs.** KV calls count toward the Workers Free limit of 50 subrequests per invocation. A memory miss costs one KV read, plus one KV write when KV misses too.

That leaves two caches: the team people directory (the teams list plus one request per team) and the song catalog (one request per hundred songs, one after another). Service types were dropped, because a KV read would replace a single request, and a miss would cost three subrequests instead of one. The song catalog is cached per credential rather than per service type, since Planning Center's catalog belongs to the organization, and for an hour, since this app never writes songs.

The shared tier never fails a request. A KV error or quota rejection is logged at `warn`, the read falls back to Planning Center, and the isolate stops using that half of KV (reads or writes) for 15 minutes. workerd ties I/O to the request that started it, so each request's services own a shared-tier session, and its writes are awaited before the response: `withPlanningCenterAccess` and demo organization loading release the services with `settleReadCaches` through `Effect.acquireUseRelease`, and the schedule and write transports run it in a `finally`.

Headroom on Workers Free ([KV limits](https://developers.cloudflare.com/kv/platform/limits/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)):

- **Writes (1,000 a day):** only a KV miss writes, at most once per scope and key per TTL window across all isolates. With a 5-minute team directory and a 1-hour song catalog, one continuously active scope writes at most 13 times an hour, so the quota covers about 75 fully active scope-hours a day. A scope changes whenever the user's access token does (every 2 hours for OAuth). Past the quota, writes stop and reads come from Planning Center.
- **Reads (100,000 a day):** at most one per shared cache on a memory miss, so at most two per request.
- **Subrequests (50 per request):** at most two extra per shared cache in a request. A team directory hit replaces 1 + T requests (13 for 12 teams); a song catalog hit replaces about 12 sequential pages.

The Cache API was rejected: Alchemy's `Cloudflare.cache()` is Workers Cache for a Worker's own HTTP responses (API responses are `private, no-store`), and `caches.default` is per location, only works for Workers on a custom domain (this Worker is reached only through service bindings), and also counts toward the subrequest limit. On Workers Paid, the shared tier could cover more caches if mutations published invalidation markers.

## Migration invariants

Each migration layer owns a complete vertical slice: contract, application program, oRPC procedure, web caller, tests, and deletion of the replaced REST route. Do not leave a second business implementation behind as a compatibility path. Better Auth routes, liveness health checks, and the OpenAPI reference are the only intentional non-oRPC HTTP surfaces after cutover.
